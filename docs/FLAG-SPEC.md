# 严格土耳其国旗 · 几何规格与实现说明

> 负责人：flag-engineer ｜ 代码：`js/flag.js`（`PDT.Flag`）、`assets/flag/turkish-flag.svg`
> 本文是与 `docs/CONTRACT.md` 配套的实现级规格。**唯一事实来源仍是 CONTRACT.md**，本文只记录几何依据与自测。

## 0. 一句话结论

所有几何以 **旗高（旗杆侧宽）G = 1** 归一化，旗长 L = 1.5 G（**高:宽 = 2:3**）；
月牙外圆半径 G/4、内圆半径 G/5、两圆心相距 G/16；五角星外接半径 G/8、星心距旗杆 197/240 G，
**星有一个尖角正对旗杆（左），不是尖朝上**；官方红 `#E30A17`。
渲染只允许「单一缩放因子 + 居中平移」，任何尺寸下都等比、绝不拉伸。

### 构造图上的字母 ↔ 本实现的量（法条原值）

| 字母 | 法条定义 | 值（G=1） |
|---|---|---|
| G | 旗宽（旗杆侧边长）= 归一化基准 | 1 |
| L | 旗长 = 3/2 G | 1.5 |
| A | 旗杆边 → 月牙**外**圆圆心 | 1/2 G = 0.5 |
| F | 月牙外圆直径 | 1/2 G = 0.5 |
| D | 月牙内圆直径 | 2/5 G = 0.4 |
| C | 月牙内外圆圆心距离 | 1/16 G = 0.0625 |
| B | 五角星外接圆直径 | 1/4 G = 0.25 |
| E | 内圆 → 星外接圆的距离 | 1/3 G = 1/3 |

> **关于 E 的一处坑**：把 E 按字面理解成「内圆右缘 + G/3 = 星外接圆左缘」，星心会跑到 1.2208 G，
> 与官方参考实现（星心 0.8208 G）差 0.4 G，也与维基正文「星左尖只探入缺口线 0.0154 G」自相矛盾。
> 反解官方构造图坐标可知：**E 实际是「内圆左缘 → 星外接圆左缘」的水平距离**
> （内圆左缘 0.5625−0.2 = 0.3625 G；星外接圆左缘 0.820833−0.125 = 0.695833 G；差正好 0.33333 G = G/3）。
> 本实现以**坐标实测值**为准，E 仅作为交叉校验。

| 白 | `SPEC.white` | #FFFFFF | — |

**3 个最关键的位比**（外行最容易画错的三个地方）：

1. **月牙外圆半径 / 旗高 = 1/4**（= 0.25）——月牙比想象的小；内圆半径 / 外圆半径 = **4/5**（= 0.8）。
2. **星外接半径 / 旗高 = 1/8**（= 0.125），且 **星心 x = 197/240 G ≈ 0.8208 G**（不是 0.75，也不是「贴着月牙」）。
3. **星左尖探入月牙缺口线 0.01542 G**（921/60000 ≈ 0.0154）——「星嘴对嘴咬进月牙开口」这一点是国旗的灵魂，画歪立刻不像。

### 星尖朝向（最容易画错的一条）

**土耳其国旗的五角星不是「尖朝上」，而是一个尖角水平指向旗杆（左方，180°）。**

三条独立证据：

1. 官方构造图里星是用 `transform="translate(17) scale(30) rotate(-90)"` 把一个「尖朝上」的单位星
   逆时针转了 90° 再放的——`rotate(-90)` 之后，「尖朝上」变成「尖朝左」。
2. 参考实现 `Flag_of_Turkey.svg` 的星形路径解出 5 个外接点角度为 `{180°, 252°, 324°, 36°, 108°}`：
   有 180° 这个尖，**没有任何一个尖是 270°（正上方）**。
3. 维基正文的校验句「the left point of the star intrudes about 0.0154 G beyond that line」
   只有在星存在一个「左尖」时才成立；本实现星左尖 = 0.695833 G，缺口线 = 0.71125 G，差 0.015417 G，吻合。

> ⚠️ **与 CONTRACT.md §5.1 的措辞有冲突**：契约写的是「正五角星且**一角朝上**」。
> 用户原话是「国旗展示要严格」，法条与官方构造图才是严格的定义，所以 `starTipAngleDeg` 取 **180°（尖朝旗杆）**。
> 如果团队最终决定按契约字面走，只需把 `js/flag.js` 里 `BASE.starTipAngleDeg` 改成 `-90` 一处即可（其余代码全跟随）。
> 已同步告知 lead。

## 3. 换算过程

### 3.1 月牙两个尖（两圆交点）

设外圆圆心 O=(A, G/2)、半径 R=G/4；内圆圆心 I=(A+C, G/2)、半径 r=G/5，两心水平距离 d=C=G/16。
交点的 x 偏移：

```
dx = (d² + R² − r²) / (2d)
   = (0.0625² + 0.25² − 0.2²) / (2×0.0625)
   = 0.02640625 / 0.125 = 0.21125
cuspX  = 0.5 + 0.21125 = 0.71125 G          (对应参考文件 42675/60000)
cuspY  = ±√(R² − dx²) = ±√(0.0625 − 0.0446266) = ±0.1336915 G   (对应 ±8021.49/60000)
```

`cuspX` 与 `cuspYoff` 在 `js/flag.js` 里是**由上面公式现算的**，不是手抄常数，所以自检能抓到自己写错。

### 3.2 星心 197/240 G 的来历

官方参考实现：星心 x = 49250（G=60000）→ 49250/60000 = 197/240。
等价写法：`A + C + dx` = 0.5+0.0625+0.21125 = 0.77375，再右移 0.0470833…… 不好看，故直接记 **197/240**。
自检里同时校验「星左尖超缺口线 0.01542 G」这个官方特征值，等于把 197/240 与法条描述绑在一起。

### 3.3 正五角星内接半径

正五角星（{5/2} 星形）凹点/尖点半径比 = cos 72° / cos 36° = 0.309017 / 0.809017 = **0.3819660**。
本实现按 10 个顶点输出实心多边形（5 尖 r=G/8，5 凹 r=0.0477458 G），与参考实现的 5 点自交路径（nonzero 填充）形状等价。

### 3.4 构造图坐标系换算

构造图 `viewBox="-198 -130 388 260"` 里旗面是 `x=-180..180, y=-120..120`，即 **G=240**、旗长 360=1.5G。
换算规则：`归一化x = (x_sheet + 180) / 240`（旗面左缘归零）、`归一化y = (y_sheet + 120) / 240`。
校验三点：

| 构造图坐标 | 换算 | 归一化值 |
|---|---|---|
| 外圆 cx = −60 | (−60+180)/240 | **0.5** ✅ |
| 内圆 cx = −45 | (−45+180)/240 | **0.5625** ✅ |
| 星心 cx = 17 | (17+180)/240 | **0.820833** ✅ |

参考实现（`viewBox="0 -30000 90000 60000"`，G=60000）同理：`归一化x = x/60000`，如 42675/60000 = 0.71125 ✅。

## 4. 怎么保证「绝不拉伸」

三条入口全部只有一个缩放因子：

1. **`fitBox(w,h)`**（唯一定义处）：
   `g = min(w / 1.5, h / 1)`，`x = (w − 1.5g)/2`，`y = (h − g)/2`；返回 `{g, sx:g, sy:g, x, y}`。
   先取小者 → 只会「装不满」，永远不会溢出；再居中 → 上下/左右留边。
2. **SVG**：`<g transform="translate(x y) scale(g)">`，`scale()` 只有一个参数 = 等比；
   外层 `<svg viewBox>` + `preserveAspectRatio="xMidYMid meet"`；旗面本体永远是 `1.5 × 1`。
3. **canvas**：`ctx.translate(x,y); ctx.scale(g,g);` 然后在 G=1 的坐标系里画 `1.5 × 1` 的旗面；
   `canvas.width/height = round(css × dpr)`，再 `ctx.setTransform(dpr,0,0,dpr,0,0)` —— **dpr 也是各向同性的**。
   只改位图尺寸，不写 CSS `width/height`，所以显示尺寸由调用方（UI）控制，不会二次拉伸。

实测（`selfCheck` + 临时断言脚本）：

| 请求尺寸 | 实际旗面 | 偏移 | 结论 |
|---|---|---|---|
| 1200×800 | 1200.000 × 800.000 | 0, 0 | 精确 3:2 |
| 400×400 | 400.000 × 266.667 | 0, 66.667 | 上下留边，不压扁 |
| 1000×200 | 300.000 × 200.000 | 350, 0 | 左右留边 |
| 37×911 | 37.000 × 24.667 | 0, 443.167 | 极小尺寸仍 1.5 |

## 6. 彩蛋特效（`easter-egg.png`）如何保证国旗不变形

彩蛋主体换成了重绘梗图 `assets/img/merge/easter-egg.png`（960×1280，粉色派大星抓着
紫/黄绿/青三色条纹伞冠大笑）。**画面里的月牙与五角星仍然不是另画的素材**，
而是 `PDT.Flag.geometry` 的同一套法条常数，只有一个缩放因子。

### 6.1 三道防线

1. **几何同源**：`drawCrescent()` / `drawStar()` 直接读 `PDT.Flag.geometry`
   （`PDT.Flag` 缺失时用同常数的兜底副本），只做
   `translate → rotate → 单一 scale(k) → translate(−outerCx, −cy)`；
   `k = 落点半径 / outerR`，没有任何 `scale(sx, sy)`。
2. **相对关系硬算**：五角星落点不是手调的，而是
   `星心 = 月牙心 + (starCx − outerCx) · k = 月牙心 + 0.320833k`（同一个 y），
   星外接半径恒为月牙外半径的 0.5 —— 与国旗原图完全一致，换任何视口都不变。
3. **飞行只允许刚体变换**：飞入时缩放 `0.52k → k`（星 `0.45k → k`）、旋转 `−0.52rad → 0`（星 `0.9 → 0`），
   全程单一缩放因子 + 旋转，不存在非等比插值。

### 6.2 落点怎么定（PIL 实测，不是目测）

对 `easter-egg.png` 做了像素级拟合（青色天空掩膜 + 条纹色掩膜，最小二乘拟合圆）：

| 对象 | 圆心（原图像素） | 半径 | 残差 |
|---|---|---|---|
| 伞冠带**外**缘 | (485, 388) | 375 | 平均 4.4 px |
| 伞冠带**内**缘 | (465, 577) | 384 | 平均 6.7 px |
| 带厚 | — | 中位数 173 px | — |

据此把月牙外圆放在 **(387, 350) r = 200**（原图像素）：上弧扣进伞冠带内侧、
下弧最低点 550 仍高于派大星头顶（肤色包围盒 y 从 575 起），不压角色。
换算成比例写死在 `EGG_GEO` 里，跟着卡片等比缩放：

```js
EGG_GEO = { cx: 387/960, cy: 350/1280, r: 200/960,
            arc: { cx: 465/960, cy: 577/1280, r: 384/960, a0: -146.4, a1: -27.2 } }
```

`arc` 是伞冠带内缘的**真实圆弧**。落位后有一道暖白光**从中间向两端沿这条真实弧线铺开**
（0.24 时长），把「月牙 = 伞冠的弧」这件事画实；同时月牙自身外圆再走一遍 295.35°「封弧」。

### 6.3 卡片本身也不变形

梗图按「高 = 视口 72%、比例 3:4、圆角卡片」渲染，卡片只有
`translate + rotate + scale(s)`（`s` 单一）；宽高超出视口时按比例回退（`cw > 0.92w` 或 `ch > 0.88h`），
不会出现只压宽或只压高。

### 6.4 缺图必须优雅降级

`preload()` 依次尝试 `easter-egg.png` → `easter-egg.webp`，上限 `opts.imageTimeout`（默认 700ms），
任一环节失败/超时 → `st.egg = null` → 回退到**程序化粉色伞**（内缘正好压在月牙外圆上，重合依旧成立），
时间轴照常从 0 跑起，`play()` 一定 resolve，绝不卡住。

> 顺带一个坑：`assets/img/merge/spark.png` 是**不透明深色底 + 亮斑**（corner 像素 `[1,0,3,255]`，
> 53% 像素接近纯黑），靠 `globalCompositeOperation='lighter'` 加法混合出光。
> 想把它染成金色**必须用 `multiply`**（保亮度）；用 `source-in` 会把深色底一起染亮成方块。

## 7. 遗留风险

1. **星尖朝向与 CONTRACT.md 字面冲突**（法条=尖朝旗杆，契约=尖朝上）。已按「严格」取法条，并在 §2 写明改法；
   若 QA 按契约字面断言「尖朝上」会误判，需 lead 拍板。
2. `starCx` 用的是参考实现反解值 197/240 G，而法条只给了 A/B/C/D/E/F + L 的组合，没有直接给星心坐标。
   已用「星尖超缺口线 0.01542 G」与 lead 的独立解算交叉验证，但不排除有比 Commons 更原始的官方图另有微差（量级 < 0.001 G）。
3. 官方红 `#E30A17` 是 Pantone 186C 的 sRGB 近似；印刷/宽色域屏上的「官方红」另有 CMYK/Hexachrome 换算，
   本项目只做屏幕显示，用 sRGB 即可。
4. 本模块只做「画」；卡片里 `flag` 的摆放/裁切由 ui-shell 决定，只要它不写死 `width`/`height` 去压扁
   （建议 `aspect-ratio: 3/2` 或 `object-fit: contain`），就不会破坏等比。
5. 彩蛋的月牙与伞冠**内缘**不是同一曲率（月牙 r=200 px vs 伞冠内缘 r=384 px，同心同弧度不可能，
   因为法条月牙要绕 295°、伞冠只张 192°，且整个星月要能落在伞内的空白区）。
   现在的解法是「上弧扣进伞冠带 + 落位后沿伞冠真实内缘扫光」来讲清「月牙 = 伞冠的弧」；
   若用户要求两弧完全共圆，只能放大月牙，届时月牙下弧会压到派大星身上，需要改构图（例如把卡片上移/裁切）。
6. `easter-egg.png` 实际是标准 PNG（960×1280，alpha 242~255），可放心用；
   但**换素材时注意是否变成 WebP**（读图工具会把它显示成 webp），若真换成 WebP 而服务器按 `.png`
   发 `Content-Type: image/png`，部分浏览器会解码失败 —— 代码里已备 `easter-egg.webp` 第二候选 + 程序化兜底。
